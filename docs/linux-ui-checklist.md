# Linux UI checklist

Every user-visible feature of upstream macOS agterm (v0.36.0), with the form it takes in the GTK4/libadwaita build and
a manual check against upstream's behavior. The suite has no Linux UI driver (`tests/ui` skips on Linux), so this list
is how the UI is verified: Task 36 walks it and fixes or records every gap with ⚠️.

Sources, all under `.upstream/agterm`: `site/docs.html` (the user guide), `.claude/rules/*.md` (per-subsystem
contracts), `agterm/Views/*`, `agterm/agtermApp+Menus.swift`, and `conformance/ui-ids.yaml` (the accessibility ids
upstream exposes). The fork's UI (`../agterm-linux`) is only a hint for the GTK form.

How to read it:

- **GTK form**: the widget or idiom standing in for the AppKit/SwiftUI one. Where a control carries one of upstream's
  accessibility ids, the GTK widget's name is that id (`gtk_widget_get_name`), so a future UI driver can find it.
- **Check**: what to do and what upstream does, which the GTK build must match.
- **Built in**: the task that builds it; a later task's number means not built yet at the time of writing. `v0.36
  sync` marks what the v0.35.1 → v0.36.0 upstream sync ported; those rows and parts of rows were read against the
  code once every port of that sync had merged.
- **Walk (Task 36)**: the row read against the code and upstream's sources: ✅ the GTK form exists and matches the
  check as far as the code shows (the hands-on check still wants a desktop session), 🔧 a gap Task 36 fixed, ⚠️ a gap
  or exception recorded and left open, "pending Task N" a feature another task builds. The walk ran before Tasks 26.1,
  34 and 35 merged; their rows were read again against the merged code when Task 36 merged.
- Launch for a walk with `scripts/run-gtk-dev.sh`, the GPUI build with `scripts/run-gpui-dev.sh` (never by hand while
  the installed fork runs).
- ⚠️ Across rows: upstream's accessibility ids are set as widget names on the sidebar, the settings, the welcome, the
  title bar's buttons and popover rows, and the zoom and dashboard exit buttons, but not yet on the ask dialog, the
  picker, the dashboard grid, the zoomed terminal, the HTML overlay, the search bar, the palettes or the Ctrl-Tab
  switcher (`conformance/ui-ids.yaml` lists them); they matter once a Linux UI driver exists.

## Settings (`SettingsView.swift`, `SettingsModel.swift`, `settings.md`)

One `adw::PreferencesDialog`, searchable, upstream's six tabs as pages in upstream's order, opening on General. Every
edit writes `settings.json` at once (a control's default value is stored as nil, except the font size, stored
explicitly so it beats `ghostty.conf`) and applies live; a change made
elsewhere (`theme.set`, `sidebar.flagged-layout`, `browser.links`) shows in the open dialog.

GPUI (Task 25, `crates/agterm-gpui/src/settings/`): at the user's request (2026-10-16), not a window of its own as
upstream's Settings scene but a modal popup inside the agterm window it was opened from (a separate window drifted off
to a tiling compositor's next column): the native panel centered over a dimmed layer that takes every click, 540x680 as
upstream's window and shrinking to leave a 16 px margin in a smaller window, a title row (Settings, a close button
`settings-close`) over upstream's six tabs as a glyph-over-label strip in upstream's order, opening on General, each
page a scrolling grouped form of titled boxes in the chrome's colors; every control carries upstream's accessibility id
as its element id. The popup holds the window's keyboard while it is up (no keymap chord, Ctrl+Tab or terminal key
reaches past it; a GUI ask, a picker, the palette or an alert arriving over it takes the keyboard and gives it back, and
so does a control in it that held the keyboard and is no longer drawn, as on a tab change); Escape, the
close button and a click outside the panel close it and the shown terminal takes the keyboard back. One popup in the
app, as upstream's one Settings window: Settings… while it is up brings its window to the front with the popup holding
the keyboard; it goes with its window. Each page describes its rows from a snapshot of the core (`form.rs`); an edit
posts one `SettingsChange` (or a Reload) to the core, and the windows' sync after every task hands the open popup a
fresh snapshot, so every control reads back what the core holds and a change made elsewhere (a command, a config
reload, a light/dark flip) shows at once; the sliders and color wells are set from it after every edit, so one the
core leaves unchanged snaps back. The pickers' menus, the switches, the sliders and the color pickers are gpui-kit's,
in the chrome's light or dark colors (`chrome/kit.rs`, row "Window chrome" below). No search field (upstream's tabs
have none).
